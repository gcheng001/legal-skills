# Prepare Hearing Record

## 目标

基于案件现有材料，直接形成可交付的 Markdown《庭审记录》，服务庭前梳理、庭上补记和庭后复核。默认输出应可直接导入 WPS 生成思维导图。

## 先读取必要上下文

1. 确定案件目录、用户代理立场、开庭日期和输出目录。
2. 若用户在既有案件目录中续办，先读取目录内的工作约定和状态文件；任务涉及“案件OS”“九步法”或存在案件OS产物时，先读取 live `~/.codex/skills/case-os/SKILL.md`，按其断点恢复顺序处理，不重复 OCR 或全卷重扫。
3. 仅读取生成庭审记录所必需的材料：
   - 传票、开庭通知或法院送达材料；
   - 起诉状、反诉状及变更诉请材料；
   - 答辩状或已确认答辩要点；
   - 双方证据清单、已形成的质证意见；
   - 与发问、辩论或金额口径直接相关的争点分析材料。
4. 如关键事实存在冲突，以原始法院文书、签章文件或经律师确认的最新材料为优先依据；在交付汇报中指出冲突，不把核验说明塞入正式记录正文。

## 直接生成成品

- 用户要求生成庭审记录时，直接生成 Markdown 成品，不先输出指令词或空方案。
- 优先在案件目录的 `分析材料/` 中写入成品；用户指定目录时按其要求落盘。
- 文件名使用：

```text
庭审记录_YYYY年M月D日_原告简称诉被告简称.md
```

- 日期优先采用开庭日期；尚无开庭日期时采用生成日期，并在正文的开庭信息处留空。
- 名称使用能够识别案件的简称，不用冗长全称作为文件名。
- 文内主标题固定为：

```markdown
# 庭审记录 原告简称诉被告简称
```

## 使用固定结构

以 [assets/庭审记录模板.md](assets/庭审记录模板.md) 为基础生成正文，并严格保留以下十个一级节点：

1. `案件信息`
2. `诉讼请求`
3. `答辩意见`
4. `原告举证`
5. `被告质证`
6. `被告举证`
7. `原告质证`
8. `法庭调查`
9. `辩论意见`
10. `需补充事项`

`##` 一级章节沿用中文顺序编号；其下的 `###` 与 `####` 子标题不得添加阿拉伯序号，以便庭审过程中自由插入节点。

## 填写规则

### 案件信息

- 只列案号、案由、原告、原告代理人、被告、被告代理人、审判员、书记员、开庭时间及地点。
- 原告、被告仅列名称，不扩展信用代码、住所、法定代表人等资料，除非用户明确要求。
- 未能从可靠材料确认的人员或时间地点，保留横线填写位；不要填写“待确认”说明，也不得凭 OCR 猜测。

### 诉讼请求与答辩

- 诉讼请求按起诉状逐项照录，不附带计算分析或质证评论。
- 答辩意见概括主要争点和请求即可，完整论证留给正式答辩状或代理词。
- 对主位/备位或递进备位的金额口径，写明择一适用，不得叠加造成重复扣减。

### 举证与质证

- 按实际证据清单逐项列示原告举证及被告举证的名称与证明目的，不虚构缺失证据。
- 默认被告视角时，对原告每项证据分别写出`真实性`、`合法性`、`关联性`意见；对被告证据下的原告质证保留三性记录位。
- 用户代表原告时，仍维持上述法庭顺序，但将己方需提前准备的三性质证写在`原告质证`章节，对对方尚未实际发表的意见保留记录位。
- 只有用户明确要求模拟对方质证时，才可预写对方可能质证观点，并应使用中性准备口径。

### 调查、辩论与补充事项

- 可根据争点和证据预填原告可能发问、被告拟发问、法庭可能发问，以及双方可能的辩论主线，便于庭前评估。
- 发问与辩论的预填内容不得表述为已经发生的庭审事实或法院意见。
- 预列可能要求双方补交的材料，并始终保留法庭当庭确定的提交方、材料名称、期限和备注记录位。

## 质量门禁

生成前和交付前必须读取 [references/质量门禁与常见错误.md](references/质量门禁与常见错误.md)，并检查：

- 文件名和主标题采用简称格式；
- 十个一级节点齐全；
- 子标题不存在阿拉伯数字序号；
- 代表方质证意见按证据覆盖真实性、合法性、关联性；
- 法庭调查、辩论意见和可能补充事项已结合案件内容填入；
- 正式正文没有“庭前预测稿”“非实际庭审笔录”“已确认/待确认”等说明标签；
- 证据证明力表述未越过现有材料。

## 输出与写回

1. 将成品文件写入案件目录。
2. 如案件目录存在日志或案件OS写回要求，记录成品路径、未确认事项及需庭后补充的节点。
3. 向用户报告成品路径及仍需现场填写的内容；法律结论与事实信息需以原件、庭审陈述和律师复核为准。
