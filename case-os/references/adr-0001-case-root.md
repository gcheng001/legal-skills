# ADR-0001：案件扫描根迁移至外置硬盘，并以配置文件驱动

- **状态**：Accepted
- **日期**：2026-07-04
- **决策者**：高澄
- **关联**：`redlines.md`（文件夹命名铁律）、`agents/weekly-scan/AGENT.md`

## 背景

案件文件原存于内置盘 `~/Documents/百度网盘/高澄/案件/`（百度网盘同步），因内置盘空间不足，已整体迁至外置硬盘 `/Volumes/移动硬盘/我的坚果云/工作文件/案件材料/`（坚果云同步），并按案件类型多了一层分类（民事/刑事/仲裁/执行…）。Obsidian/LifeOS 库仍在原内置盘路径，未迁移。

case-os 的三个脚本（`scripts/scan_case_folders.py`、`agents/weekly-scan/scan.py`、`agents/court-sms-monitor/monitor.py`）原本把扫描根硬编码为旧路径，迁移后扫描扑空；且原逻辑 `if not root.exists(): continue` 在硬盘未连接时会**静默扫出 0 案**，对依赖它提醒文书期限的律师构成风险。

## 决策

1. **路径存储：单一配置文件**。新建 `data/scan-roots.txt`（每行一个绝对路径，`#` 注释），三个脚本统一通过 `_load_scan_roots()` 读取。
2. **当前值**：`/Volumes/移动硬盘/我的坚果云/工作文件/案件材料`。
3. **脱机守卫**：当配置存在但所有扫描根都不可访问时（典型场景：移动硬盘未连接），周期性扫描脚本（scan_case_folders / weekly-scan）写入状态文件并退出，不再继续；monitor.py（长驻短信监听）只警告不退出——其主职读 SMS 库、不依赖案件根，案件匹配降级但不影响告警链路。
4. **递归扫描不变**：仍按 `rglob("CLAUDE.md")` 识别案件夹，因此新家多出的"案件类型"分层不影响识别。

## 备选方案与取舍

- **直接硬编码新路径**：放弃。外置硬盘路径不稳定（盘符可能变为"移动硬盘 1"、可能换盘、可能再迁移），每次变动要改三个脚本。
- **软链**（旧路径 `案件` → 新盘）：放弃。旧路径仍在百度网盘同步目录下，软链会被百度网盘客户端尝试跟随同步，有数据风险；且脱机时软链同样悬空，不解决静默失败。
- **单一配置文件**（本方案）：路径再变只改一个 txt，适合非技术用户；代价是三个脚本各内联同一份 ~12 行加载器（三个脚本分布在不同目录、无共享模块机制，内联比新建跨目录 import 更稳）。

## 后果

- **正向**：路径迁移一处可改；硬盘脱机有可见警告；未来再迁移成本低。
- **负向**：`_load_scan_roots()` 在三个脚本里各有一份，逻辑变更需同步三处（已通过统一命名 `_load_scan_roots` / `SCAN_ROOTS_FILE` 降低漂移风险）。
- **遗留**（不在本 ADR 范围）：
  - `scan_case_folders.py` 的待处理队列写到 `~/.codex/skills/case-os/data/pending-files.json`，而 `weekly-scan/scan.py` 读的是 `~/.claude/skills/...`——两端队列路径不一致，pre-existing bug，待单独修复。
  - `memory.md` 固化规则"项目文件统一放在 ~/Documents/百度网盘/高澄/"已部分失效（案件已迁出，Obsidian 仍在），待主人确认是否更新该规则。
